01The thesis

착안점

CORBA already has what AI agents need, and nobody noticed. The Model Context Protocol standardized runtime tool discovery in 2025: a client calls tools/list and receives a live catalog of callable operations with schemas. CORBA shipped that in 1996 — the Interface Repository, with the Dynamic Invocation Interface as its matching call path.

CORBA는 AI 에이전트가 필요로 하는 것을 이미 갖고 있습니다. 아무도 주목하지 않았을 뿐입니다. MCP는 2025년에 런타임 도구 발견을 표준화했지만, CORBA는 1996년에 이미 제공했습니다 — Interface Repository와, 대응하는 호출 경로인 Dynamic Invocation Interface입니다.

Proposition 1 · 명제 1

CORBA is a runtime self-describing type system. IFR + TypeCode + DII/DSI + DynAny let a caller discover and correctly invoke an interface it has never seen, with zero generated code. The discovery mechanism does not need inventing.

CORBA는 런타임 자기기술 타입 시스템이다. IFR + TypeCode + DII/DSI + DynAny 조합이면 한 번도 본 적 없는 인터페이스를 생성 코드 없이 발견해 정확히 호출할 수 있다. 발견 메커니즘을 새로 발명할 필요가 없다.

Proposition 2 · 명제 2

For an LLM, IDL's verbosity is an asset. The strictness that drove humans to REST is exactly what makes machine-generated interfaces verifiable. An IDL compiler rejects malformed IDL deterministically, every time — a ground-truth oracle that OpenAPI-based approaches lack.

LLM에게 IDL의 장황함은 자산이다. 인간을 REST로 몰아낸 그 엄격함이 기계 생성 인터페이스를 검증 가능하게 만든다. IDL 컴파일러는 잘못된 IDL을 예외 없이 거부한다 — OpenAPI 기반 접근이 갖지 못한 정답 채점기다.

Proposition 3 · 명제 3

The bottleneck is specification quality, not code generation. AutoMCP compiled 5,066 endpoints across 50 real APIs: 76.5% worked immediately, 99.9% after ~19 lines of spec fixes per API. Failures were spec defects — missing security schemes 62%, undocumented headers 47%, bad base URLs 41%.

병목은 코드 생성이 아니라 명세 품질이다. AutoMCP는 실제 API 50개·엔드포인트 5,066개에서 즉시 동작 76.5%, API당 약 19줄의 명세 수정 후 99.9%를 기록했다. 실패는 전부 명세 결함이었다.

Proposition 3 sets the priority: the first-class deliverable is a semantic annotation vocabulary, not a code generator.

명제 3이 우선순위를 정합니다 — 1급 산출물은 코드 생성기가 아니라 의미 어노테이션 어휘입니다.

S4 is the safety belt · S4가 안전벨트

An LLM writes plausible IDL that may be wrong; an IDL compiler rejects wrong IDL every single time. That asymmetry — probabilistic synthesis, deterministic verification — is the trust model the whole system rests on. Everything upstream of S4 is allowed to be uncertain because S4 is not.

LLM은 그럴듯하지만 틀릴 수 있는 IDL을 씁니다. IDL 컴파일러는 틀린 IDL을 100% 거부합니다. 이 비대칭 — 확률적 합성, 결정론적 검증 — 이 시스템 전체의 신뢰 모델입니다. S4 상류가 불확실해도 되는 이유는 S4가 그렇지 않기 때문입니다.

03SIDL — the semantic layer

의미 계층

IDL nails syntax and says nothing about meaning. long transfer(in long acct, in long amt) is perfectly typed and tells an agent nothing about whether the unit is won or cents, whether it is idempotent, whether it is destructive, or whether the argument is PII. SIDL closes that gap using OMG IDL 4.x's own @annotation construct — a standard feature, not an extension.

IDL은 구문은 완벽히 잡지만 의미는 말하지 않습니다. 단위가 원인지 센트인지, 멱등한지, 파괴적인지, 인자가 PII인지 — 에이전트가 알아야 할 것은 하나도 담지 못합니다. SIDL은 OMG IDL 4.x의 표준 @annotation 문법으로 이 간극을 메웁니다.

// sidl_annotations.idl
@annotation ai_desc       { string  text;  };  // intent in prose    / 자연어 의도
@annotation ai_unit       { string  unit;  };  // KRW, meter, ms     / 단위
@annotation ai_effect     { string  kind;  };  // pure|read|write|destructive
@annotation ai_idempotent { boolean value; };  // retry safety       / 재시도 안전성
@annotation ai_pii        { string  level; };  // none|low|high
@annotation ai_authz      { string  scope; };  // required permission/ 필요 권한

module bank {
  @ai_desc("Transfers funds between accounts. Rolls back in full on failure.")
  interface Transfer {
    @ai_effect("destructive") @ai_idempotent(FALSE)
    @ai_authz("bank.transfer.write")
    void execute(
      @ai_pii("high") in long from,
      @ai_pii("high") in long to,
      @ai_unit("KRW") in long amount
    ) raises (InsufficientFunds, AccountFrozen);
  };
};

One vocabulary drives both directions: at runtime it is the tool description an agent reads; at build time it is the source for generated contract tests and guardrails.

하나의 어휘가 양방향을 구동합니다. 런타임에는 에이전트가 읽는 도구 설명이고, 빌드 타임에는 계약 테스트와 가드레일을 생성하는 근거입니다.

04The licensing constraint that reshaped the plan

계획을 다시 짜게 만든 라이선스 제약

Policy: every shipped component is MIT or MIT-equivalent, or it is written here. That has one hard consequence worth stating plainly.

방침: 배포하는 모든 구성요소는 MIT 또는 MIT 동등이거나, 직접 작성한다. 여기에는 분명히 밝혀 둘 결과가 하나 있습니다.

Verified 2026-08 · 확인 완료

No CORBA ORB is available under MIT. Every mature open-source ORB is excluded, so the ORB core is built in-house.

MIT로 제공되는 CORBA ORB는 존재하지 않습니다. 성숙한 오픈소스 ORB가 전부 배제되므로 ORB 코어는 직접 구현합니다.

Why this is survivable · 왜 감당 가능한가

Interoperability requires no license. GIOP/IIOP is a published OMG specification; implementing the wire protocol creates no obligation toward TAO, omniORB or JacORB — no linking, no derivation, no redistribution. Those ORBs move from the dependency list to the interop test matrix: pulled into throwaway CI containers to verify wire correctness, never shipped.

상호운용에는 라이선스가 필요하지 않습니다. GIOP/IIOP는 공개된 OMG 명세이며, 와이어 프로토콜 구현은 TAO·omniORB·JacORB에 대해 어떤 의무도 발생시키지 않습니다. 링크도, 파생도, 재배포도 없기 때문입니다. 이들은 의존성에서 상호운용 테스트 매트릭스로 이동합니다 — CI 컨테이너에서 와이어 정확성 검증에만 쓰고 배포물에는 넣지 않습니다.

Cost: ~15 additional weeks — CDR, GIOP framing, IIOP transport, IOR handling, POA and the type registry all become first-party work. Benefit: owning the parser makes the annotation fallback possible, and owning the registry means the semantic catalog is the registry rather than a layer bolted onto a foreign IFR.

비용: 약 15주 추가 — CDR, GIOP 프레이밍, IIOP 전송, IOR 처리, POA, 타입 레지스트리가 전부 자체 작업이 됩니다. 이득: 파서 소유가 어노테이션 폴백을 가능하게 하고, 레지스트리 소유는 시맨틱 카탈로그가 외부 IFR에 덧붙는 계층이 아니라 레지스트리 그 자체가 되게 합니다.

Dual-path binding이중 경로 연동

Pure code generation breaks automation the moment a schema changes; pure dynamic invocation is too slow for a hot path. Running both and promoting between them satisfies each constraint where it actually binds.

순수 코드 생성은 스키마가 바뀌는 순간 자동화가 깨지고, 순수 동적 호출은 임계 경로에 쓰기엔 느립니다. 둘 다 운영하고 사이에서 승격시키면 각 제약이 실제로 작용하는 지점에서 각각 해소됩니다.

Dynamic path · 동적 경로Static path · 정적 경로
MechanismDII + DynAnyGenerated stubs
Code generatednone · 없음full · 전체
Schema changeadapts automatically · 자동 적응regenerate + redeploy · 재생성·재배포
Latencyhigher · 높음lowest · 최저
Type safetyruntime · 런타임compile time · 컴파일 타임
Best fordiscovery, experiments · 탐색·실험hot paths, real-time · 임계 경로·실시간

Promotion criteria — ≥1,000 calls/day and schema unchanged for 30 days and regression suite green. Explore dynamically, settle statically.

승격 조건 — 일 1,000회 이상 호출 그리고 스키마 30일 무변경 그리고 회귀 스위트 통과. 탐색은 동적으로, 정착은 정적으로.

Projecting into MCPMCP 투영

One tool per operation collapses at legacy scale — thousands of operations would swamp tools/list. The default projection is a generic triad — search_interfaces, describe_interface, invoke_operation — and exposure is default-deny: nothing becomes callable until explicitly allowlisted.

연산 하나당 도구 하나는 레거시 규모에서 무너집니다. 기본 투영은 범용 3종 — search_interfaces, describe_interface, invoke_operation — 이며, 노출은 기본 거부입니다. 명시적으로 허용 목록에 올리기 전에는 아무것도 호출할 수 없습니다.

Phase 0 gates the projectPhase 0가 프로젝트의 관문

  • A — GIOP interop is reachable. Hand-encode a GIOP 1.2 Request; get a correct reply from stock TAO and omniORB. If a minimal ORB cannot interoperate, the in-house path fails and the MIT-only constraint must be revisited. GIOP 상호운용이 가능한가. 최소 ORB가 상호운용되지 않으면 자체 구현 경로가 무너지고 MIT 전용 제약을 재검토해야 한다.
  • B — LLMs write compilable IDL. 20 requirements → IDL. Target ≥60% first-pass, ≥95% within three self-repair rounds. LLM이 컴파일되는 IDL을 쓰는가. 목표 1차 통과 ≥60%, 자가수정 3회 내 ≥95%.
  • C — @annotation survives real toolchains. Most deployed ORB compilers predate IDL 4. Fallback: structured comments plus sidecar YAML — viable because we own the parser. 배포된 ORB 컴파일러 대부분은 IDL 4 이전 세대다. 폴백은 구조화 주석 + 사이드카 YAML이며, 파서를 우리가 소유하므로 가능하다.
  • D — IOR addressing works under NAT/containers. An internal IP baked into an IOR is uncallable from outside; verify endpoint rewriting under Kubernetes early. IOR에 박힌 컨테이너 내부 IP는 외부에서 호출할 수 없다. K8s의 endpoint 재작성을 조기에 검증한다.

08Why CORBA in 2026

왜 지금 CORBA인가

Not nostalgia. Three concrete reasons, plus one that matters more than the rest.

향수가 아닙니다. 구체적인 이유가 셋, 그리고 나머지보다 중요한 것이 하나 있습니다.

  • The legacy is load-bearing and not going away. Naval combat systems, command and control, telecom switching, air traffic control, core banking, large physics installations — environments where a rewrite is not an option. 레거시가 하중을 지탱하고 있고 사라지지 않습니다. 함정 전투체계, 지휘통제, 통신 교환기, 항공관제, 금융 코어 — 재작성이 선택지가 아닌 환경들입니다.
  • OMG IDL 4.x is shared with DDS. Korean defense programs are standardizing on DDS-based middleware, and DDS-XTypes uses the same IDL. One pipeline serves both, turning a shrinking CORBA market into an expansion path. OMG IDL 4.x는 DDS와 공유됩니다. 하나의 파이프라인이 양쪽을 커버하므로, 축소되는 CORBA 시장이 확장 경로가 됩니다.
  • Java severed its own connection. JEP 320 removed java.corba in JDK 11, so Java legacy now needs a third-party ORB just to keep running. That forced migration is itself demand for automation. Java는 스스로 연결을 끊었습니다. JEP 320이 JDK 11에서 java.corba를 제거해, Java 레거시는 동작 유지만을 위해서도 서드파티 ORB가 필요합니다.
The reason that matters most · 가장 중요한 이유

Interfaces are increasingly called by agents rather than people. In that world a contract that is verbose but precise beats one that is terse but ambiguous. The complexity humans rejected in CORBA is the precision agents need.

인터페이스를 호출하는 주체가 점점 사람에서 에이전트로 옮겨가고 있습니다. 그 세계에서는 장황하지만 정밀한 계약이 간결하지만 모호한 계약을 이깁니다. 인간이 거부했던 CORBA의 복잡성이, 에이전트에게는 필요한 정밀성입니다.
